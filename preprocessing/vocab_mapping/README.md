# Reclaim Vocabulary Mapping 

This directory contains scripts for creating standardized vocabulary mappings for medical codes/tokens used in Reclaim project.

--- 

## Quick Start
```bash
# From preprocessing/vocab_mapping
./create_mappings.sh

# Or run individual steps with the same relative paths used by create_mappings.sh
python create_dx_mapping.py \
  --gems_file standard_vocab/diagnosis_gems_2018/2018_I9gem.txt \
  --output_dir mapping

python create_proc_mapping.py \
  --ohdsi_vocab_dir standard_vocab/ohdsi_vocab_v20250827 \
  --output_dir mapping

python create_rx_mapping.py \
  --ohdsi_vocab_dir standard_vocab/ohdsi_vocab_v20250827 \
  --output_dir mapping
```

## Local Data and Generation Policy

This folder documents the expected local file layout. The large vocabulary
inputs and generated mapping outputs are not included in this repository; users
should download the source vocabularies and generate the mapping outputs locally.

| Path | Purpose | How it is created |
|------|---------|-------------------|
| `standard_vocab/diagnosis_gems_2018/` | CMS GEMs input files and guides for ICD-9-CM to ICD-10-CM diagnosis mapping | Download from CMS, then place locally under this path |
| `standard_vocab/ohdsi_vocab_v20250827/` | OHDSI Athena vocabulary input files for procedure and drug mappings | Download from OHDSI Athena, then place locally under this path |
| `mapping/` | Generated mapping outputs consumed by preprocessing pipelines | Generated by `./create_mappings.sh` or the individual scripts above |


## Source files

**Diagnosis mapping:**
- `standard_vocab/diagnosis_gems_2018/` stores the mapping data and user guide of the 2018 (up-to-date) general equivalence mappings (GEMs) from [CMS](https://www.cms.gov/medicare/coding-billing/icd-10-codes/icd-10-cm-icd-10-pcs-gem-archive). Files within this folder are downloaded from the [CMS GEMs archive](https://www.cms.gov/medicare/coding/icd10/downloads/2018-icd-10-cm-general-equivalence-mappings.zip).
    - `2018_I9gem.txt`: ICD9CM to ICD10CM mapping file


**Procedure and drug mappings:**
- `standard_vocab/ohdsi_vocab_v20250827/` stores OHDSI standard vocabulary files used in this study from [OHDSI Athena](https://athena.ohdsi.org/search-terms/start), version v20250827.
    - `CONCEPT.csv`
    - `CONCEPT_CPT4.csv` (CPT4 concept comes separately)
    - `CONCEPT_RELATIONSHIP.csv`
    - `CONCEPT_ANCESTOR.csv`

## Scripts

### 1. `create_dx_mapping.py` - Diagnosis Code Mapping
Maps ICD-9-CM diagnosis codes to ICD-10-CM using CMS GEMs (General Equivalence Mappings)

**Key Features:**
- Preserves one-to-many mappings as separate rows (no aggregation)
- Appropriate for temporal analysis (ICD-9 used pre-2015, ICD-10 post-2015)
- Handles approximate mappings and no-map cases
- Output: `icd9_to_icd10_mapping.csv`

**GEM Flags and Relationships:**
- CMS GEMs do not use OMOP `relationship_id` values. The script parses GEM flags and assigns ReClaim relationship labels for consistency with other mapping files.
- `approximate`: `1` means the ICD-9-CM to ICD-10-CM mapping is approximate and is labeled `Maps to approximate`; `0` is labeled `Maps to`.
- `no_map`: `1` means no valid ICD-10-CM target exists; these rows are dropped.
- `combination`, `scenario`, and `choice_list`: GEM fields retained in the `*_original.csv` audit output for interpreting combination mappings, but not used to collapse diagnosis targets into grouped tokens.
  
**Rationale:** 
- Refer to `vocab_mapping/standard_vocab/diagnosis_gems_2018` for use guide of the GEMs file.
- Diagnosis mappings are intentionally handled differently from procedure and drug mappings. For diagnoses, one-to-many GEM mappings are kept as separate rows instead of being grouped with `COMBSTART`/`COMBEND` tokens. MarketScan uses ICD-9-CM codes before 2015 and ICD-10-CM codes from 2015 onward; converting ICD-9-CM history into the ICD-10-CM token format keeps diagnosis tokens more consistent over time. GEM one-to-many targets are plausible alternative mappings rather than parts of one compound clinical concept, so grouping them would create artificial compound diagnosis units. Preserving all valid GEM targets avoids forcing an arbitrary single target when multiple ICD-10-CM mappings are plausible, which could introduce temporal bias and hurt model generalization.

### 2. `create_proc_mapping.py` - Procedure Code Mapping
Maps procedure codes (ICD-10-PCS, ICD-9-CM, CPT4) to SNOMED using OMOP standard vocabulary

**Why SNOMED as Target Vocabulary:**
- SNOMED is the standard procedure vocabulary in OMOP CDM, providing a unified representation across different source vocabularies
- ICD10PCS cannot be directly mapped to CPT4 (no direct relationship exists in OMOP), but both can be linked through SNOMED via hierarchical relationships (`Is a`, `Has method`)
- Using SNOMED as a common target enables cross-vocabulary procedure analysis and harmonization

**Key Features:**
- Aggregates one-to-many mappings using COMBSTART/COMBEND tokens
- Priority-based deduplication (CPT4 > ICD9CM > ICD10PCS)
- CPT4 fallback for unmapped codes (preserves all CPT4 codes)
- Handles multiple source vocabularies
- Output: `proc_to_snomed_mapping.csv`

**Relationships Used:**
- Multiple relationships are included to improve mapping completeness for SNOMED. Some relationships are not direct mappings but contain hierarchical information (e.g., `Is a`, `Has method`), so `COMBSTART` and `COMBEND` tokens are used to keep grouped target concepts together.

| Source Vocab | Relationships | Rationale |
|--------------|---------------|------------------------------|
| **CPT4** | `CPT4 - SNOMED eq`<br>`Maps to`<br>`Is a`<br>`CPT4 - SNOMED cat` | Exact equivalence preferred over generic mappings or categorical relationships |
| **ICD9CM** | `Maps to` | Direct standard mapping from OMOP vocabulary |
| **ICD10PCS** | `Is a`<br>`Has method` | Type relationships (`Is a`) are more specific than methodological relationships |

**CPT4 Fallback Logic:**
- Uses LEFT JOIN to preserve all CPT4 codes, even those without SNOMED mappings
- Unmapped CPT4 codes receive fallback values:
  - `snomed_code` = `'CPT4' + concept_code` (e.g., `CPT499213`)
  - `snomed_name` = original CPT4 concept name
  - `relationship_id` = `'Not mapped'`
- **Rationale:** CPT4 is the dominant procedure vocabulary in MarketScan data (~80%). Excluding unmapped CPT4 codes would lose significant procedure information. our exploratory analysis shows that unmapped (to SNOMED) CPT can still take up to 20% of procedure in outpatient settings. The fallback creates unique identifiers that preserve the original CPT4 code while clearly indicating no SNOMED mapping exists.

**Vocabulary Priority (when same code appears in multiple sources):**
- MarketScan data can have the same code in the PROC columns that may come from different vocabularies (e.g., CPT4 and ICD9CM, since ICD9CM's `.` is removed and 5-character ICD9 codes can overlap with 5-character CPT4 codes). Unfortunately, the source vocabulary column for PROC codes is incomplete in MarketScan data, so we use predefined priority-based deduplication to resolve conflicts.
- CPT4 > ICD9CM > ICD10PCS
- CPT4 is the most specific and widely used in US healthcare billing, accounts for over 80% of our procedure codes in the MarketScan data, and has the smallest vocabulary size.
- ICD9CM has a smaller vocabulary size and can conflict with CPT4 in MarketScan data since ICD9CM's `.` is removed, so 5-character ICD9 codes can overlap with 5-character CPT4 codes.
- ICD10PCS is 7-character long and almost impossible to overlap with CPT4 or ICD9CM 
- The script also checks source-code overlap across CPT4, ICD9CM, and ICD10PCS and stops if the overlap rate exceeds the configured threshold.


### 3. `create_rx_mapping.py` - Drug Code Mapping
Maps NDC codes to RxNorm ingredients using OMOP standard vocabulary

**Key Features:**
- Two-step mapping: NDC to RxNorm Drug to RxNorm Ingredient
- Aggregates one-to-many mappings using COMBSTART/COMBEND tokens
- Handles multi-ingredient drugs
- Output: `ndc_drug_to_rxnorm_ingredient_mapping.csv`
  
**Relationships Used:**
- `Maps to` - Map NDC to RxNorm drug
- `Has ingredient` - Map RxNorm drug to RxNorm ingredient

**Rationale:** 
- NDC codes are unique drug product identifiers with no vocabulary overlap
- Two-step hierarchical mapping (NDC -> RxNorm Drug -> RxNorm Ingredient) ensures clean relationships
- Each source token maps to exactly one aggregated target by design

## Output Format

All three scripts produce mapping files with consistent 9-column structure:

| Column | Description | Example Values |
|--------|-------------|----------------|
| `source_prefix` | Token prefix for source codes | `DX`, `PROC`, `NDCNUM` |
| `target_prefix` | Token prefix for target codes | `DX`, `PROC`, `RX` |
| `source_token` | Tokenized source code | `<DX-0010>`, `<PROC-73706>` |
| `source_vocab` | Source vocabulary name | `ICD9CM`, `CPT4`, `NDC`, `ICD10PCS`, `ICD9CM`|
| `target_vocab` | Target vocabulary name | `ICD10CM`, `SNOMED`, `RXNORM_INGR` |
| `relationship_id` | Type of mapping relationship | `Maps to`, `Has ingredient`, `Not mapped`, ...|
| `num_targets` | Number of target codes | `1`, `4` |
| `target_token` | Tokenized target code(s) | `<DX-A000>`, `<PROC-COMBSTART> ... <PROC-COMBEND>`, `<PROC-CPT499213>` |
| `target_value` | Raw target code value(s) | `A000`, `113090004`, `CPT499213` (fallback) |

### One-to-Many Mapping Cases

**Key Difference:** DX keeps multiple targets as separate rows, while PROC/RX combine them into a single row with special tokens.

**DX Mapping (one source maps to multiple targets → separate rows):**

| source_token | source_vocab | num_targets | target_token | target_vocab |
|--------------|--------------|-------------|--------------|--------------|
| `<DX-01793>` | ICD9CM | 2 | `<DX-A1884>` | ICD10CM |
| `<DX-01793>` | ICD9CM | 2 | `<DX-A1889>` | ICD10CM |

**PROC/RX Mapping (one source maps to multiple targets → grouped with COMBSTART/COMBEND):**

| source_token | source_vocab | num_targets | target_token | target_vocab |
|--------------|--------------|-------------|--------------|--------------|
| `<PROC-74301>` | CPT4 | 2 | `<PROC-COMBSTART> <PROC-16278002> <PROC-71093009> <PROC-COMBEND>` | SNOMED |
| `<RX-1000030>` | RXNORM | 2 | `<RX-COMBSTART> <RX-235496> <RX-6832> <RX-COMBEND>` | RXNORM ingredient |

**CPT4 Fallback (unmapped CPT4 → uses CPT4 prefix as fallback target):**

| source_token | source_vocab | relationship_id | num_targets | target_token | target_vocab |
|--------------|--------------|-----------------|-------------|--------------|--------------|
| `<PROC-99213>` | CPT4 | Not mapped | 1 | `<PROC-CPT499213>` | SNOMED | 


### Dot Removal
All ICD codes have dots removed for MarketScan compatibility (e.g., `250.00` becomes `25000`)

## Output Files

The scripts write all generated CSVs to `mapping/`. The files below describe
the expected outputs, but these generated files are not intended to be committed
to the repository.

### Final Mapping Files Used by MarketScan Preprocessing

| File | Generated by | Purpose |
|------|--------------|---------|
| `mapping/icd9_to_icd10_mapping.csv` | `create_dx_mapping.py` | Main diagnosis crosswalk from ICD-9-CM source tokens to ICD-10-CM diagnosis tokens |
| `mapping/proc_to_snomed_mapping.csv` | `create_proc_mapping.py` | Combined procedure mapping from CPT4, ICD9CM, and ICD10PCS source tokens to SNOMED or CPT4 fallback tokens |
| `mapping/ndc_drug_to_rxnorm_ingredient_mapping.csv` | `create_rx_mapping.py` | Main MarketScan pharmacy mapping from NDC source tokens to RxNorm ingredient tokens |

### Final Mapping Files Used by External Validation

| File | Generated by | Purpose |
|------|--------------|---------|
| `mapping/rxnorm_drug_to_rxnorm_ingredient_mapping.csv` | `create_rx_mapping.py` | RxNorm drug to RxNorm ingredient mapping used when the source data already uses RxNorm drug concepts |
| `mapping/payer_concept_annotated.csv` | Manual/helper input annotated by domain experts | Maps OMOP payer concepts to ReClaim/MarketScan-like enrollment fields such as `PAYER`, `PLANTYP`, and `CAP`; used by EHRSHOT/YNHH external validation preprocessing to fill payer fields |

### Intermediate and Diagnostic Mapping Files

These files are useful for auditing, debugging, and regenerating the final
combined mappings, but they are not the primary files consumed by the main
preprocessing pipeline.

| File pattern | Purpose |
|--------------|---------|
| `mapping/*_original.csv` | Raw or lightly transformed mapping rows before conversion to the 9-column token mapping schema |
| `mapping/cpt_to_snomed_procedure_mapping.csv` | CPT4-only procedure mapping before combination into `proc_to_snomed_mapping.csv` |
| `mapping/icd9cm_to_snomed_procedure_mapping.csv` | ICD9CM-only procedure mapping before combination into `proc_to_snomed_mapping.csv` |
| `mapping/icd10pcs_to_snomed_procedure_mapping.csv` | ICD10PCS-only procedure mapping before combination into `proc_to_snomed_mapping.csv` |
| `mapping/ndc_drug_to_rxnorm_drug_mapping.csv` | First step of drug mapping: NDC to RxNorm drug |
